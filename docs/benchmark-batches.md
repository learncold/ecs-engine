# 조건별 반복 벤치마크

`scripts/run_benchmarks.py`는 단일 실험용 `App.exe --benchmark`를 조건별로
별도 프로세스에서 순차 실행한다. Windows, Python 3.10 이상과 VS2022 x64
기본 MSVC toolset의 Release 빌드가 필요하다. Python 외부 패키지는 사용하지 않는다.
연구 조건과 지표의 정의는 [연구 기준 5~6절](research-goals.md#experiments)을 따른다.

## GUI 실행

Tkinter가 포함된 Python에서 다음 명령으로 연다. `python -m tkinter`로 Tkinter 설치를
확인할 수 있다. 추가 pip 패키지는 필요 없다. 실행 파일은 먼저 Release로 빌드한다.

```powershell
python -B scripts/benchmarker_gui.py
# 지정한 설정으로 열기
python -B scripts/benchmarker_gui.py C:/Experiments/BoidsStudy
```

앱을 실행하면 프로젝트 생성·불러오기 화면이 열린다. 새 프로젝트를 저장할 폴더를
선택하거나 `project.json`이 있는 기존 프로젝트 폴더를 선택하면 메인 화면으로 진입한다.
명령 뒤에 프로젝트 폴더를 지정하면 바로 연다. 프로젝트를 열기만 해서는 측정을 시작하지 않는다.

```text
내 프로젝트/
  project.json           실험 설정·편집 중인 입력·화면 상태
  Result/
    <실행 시각-고유번호>/   실행 당시 조건·원자료·Excel·로그·복구 기록
    <다른 실행 기록>/
```

메인 화면의 두 탭은 다음 역할을 갖는다.

- **실험 설정**: 새 실험에 사용할 실행 파일, 반복·warmup·측정 step·seed·dt와 조건
  목록을 편집한다. 새 프로젝트는 빈 조건 목록으로 시작한다. 결과 저장 위치는 항상
  프로젝트의 `Result` 폴더다. 프로젝트 저장 또는 정상 종료 시 `project.json`에 저장한다.
  유효하지 않은 숫자를 편집 중이어도 그 입력을 보존하며 실행 시에는 검증한다.
- **실행**: 상단에 프로젝트 안의 실행 기록 목록과 선택 기록의 조건·로그를 표시하고,
  하단에 실행 버튼과 진행 상태를 표시한다. 기록을 선택해도 실험 설정 탭의 편집 내용은
  바뀌지 않는다. 기록별 진행 상황은 각 폴더의 완료 기록으로부터 복원한다.

실험 설정 탭에서 조건 목록을 만드는 방법:

- **새 조건 추가 / 표에 조건 추가**: 설정이나 이전 결과를 불러오면 추가 입력란은
  빈 상태로 시작한다. 기존 표를 별도의 조합으로 추측해 채우지 않는다. Boid 수·Dummy
  수·변경률을 직접 입력하고 구현을 선택하면 새 조건 수와 제외할 중복 수를 미리 표시한다.
  유효한 새 조건이 있을 때만 추가 버튼을 활성화한다.
  Dummy 목록의 `B`, `4B`는 각각 해당 Boid 수와 그 4배다. 예를 들어 Boid `512,1024`,
  Dummy `0,B,4B`, 변경률 `0,10,100`으로 조합을 만들 수 있다. Dummy 0은 변경률 0만
  추가하며 기존과 중복된 조건은 추가하지 않는다. 숫자에는 천 단위 쉼표를 넣지 않는다.
  입력만으로는 기존 표가 바뀌지 않으며 버튼을 누른 후의 표가 저장·측정 대상이다.
  목록의 행을 두 번 클릭해 개별 수정하거나 선택 삭제한다. 추가 입력란의 작성 중인 값은
  프로젝트의 편집 상태로 보존하며 실제 측정 조건에 자동으로 반영하지 않는다.
- **기존 설정 JSON 가져오기**: CLI의 기존 설정 파일을 프로젝트에 가져온다. 결과
  경로는 현재 프로젝트의 `Result`로 적용한다. **실행 설정 JSON 내보내기**는 현재의
  유효한 설정을 CLI 형식으로 내보낸다. `project.json`은 편집 상태도 포함하는 프로젝트
  형식이므로 CLI 설정과 다르다. 프로젝트 밖의 실행 기록은 자동 이동·수정하지 않는다.

실행 탭의 버튼:

- **새 실험 실행**: 실험 설정 탭의 조건으로 `Result` 아래 새 기록을 만든다. 같은 조건의
  과거 결과가 있어도 별도 기록으로 시작하며 과거 데이터는 덮어쓰지 않는다.
- **선택 기록 이어서 실행**: 선택한 기록에 보존된 당시 조건으로 재개한다. 현재 편집
  조건과 달라도 해당 기록의 조건을 사용하며 편집 탭은 그대로 유지한다. 성공 CSV를
  검증해서 건너뛰고 실패·중단된 프로세스만 재시도한다. 실행 파일·도구·Python·빌드
  설정의 일치 여부는 기존 실행기와 동일하게 확인한다.
- **중단**: 현재 App 프로세스를 종료·회수하고 결과를 저장한다. 창을 닫을 때도 같은
  절차를 기다린 뒤 프로젝트를 저장한다. 프로젝트를 다시 열면 마지막 탭·선택 기록·
  진행 상황과 편집하던 조건을 복원한다. 선택 기록을 이어서 실행하면 중단된 프로세스만
  처음부터 다시 실행한다. 저장 실패 시에는 오류를 표시하고 창을 유지한다.

전체 진행률과 성공·실패·건너뜀 횟수, 현재 조건·경과 시간을 표시하며 측정 중에는
조건 편집을 잠근다. 프로세스 안의 step 진행률은 표시하지 않는다. 완료·실패 사유는
실행 기록 탭에서 확인한다. 결과 폴더와 Excel은 버튼으로 열 수 있다.
Excel 파일이 열려 갱신할 수 없을 때의 알림도 실행 기록에 표시한다.

프로젝트 저장은 임시 파일을 완성한 뒤 `project.json`을 교체한다. 기존 전역
`out/benchmarker-gui/session.json`은 사용하지 않는다. 기록을 표시할 때는 복구 파일을
수정하지 않으며, 중간에 잘린 마지막 기록은 실행기가 재개할 때 복구한다.
프로젝트나 실행 파일의 경로가 달라지면 기존 실행기의 경로·해시 일치 검사를 통과해야
재개할 수 있다. 프로젝트 폴더 이동에 따른 과거 원자료의 경로 재작성은 지원하지 않는다.

## 빌드·검증·실행

프로젝트 루트에서 다음 명령을 실행한다. 전체 테스트에는 세 구현의 상태 동등성 검사가
포함된다. Release 전체 테스트의 `BenchmarkBatchAcceptance`도 실제 App을 사용한다.

```powershell
cmake --preset vs2022
cmake --build --preset vs2022-debug
ctest --test-dir build/vs2022 -C Debug --output-on-failure
cmake --build --preset vs2022-release
ctest --test-dir build/vs2022 -C Release --output-on-failure
python -B scripts/run_benchmarks.py benchmarks/smoke.json
```

[smoke.json](../benchmarks/smoke.json)은 16 Boid·12 Dummy, 변경률 0·40%, 세 구현을
각각 2회 실행하는 작은 검증 예시다. warmup은 7, 측정은 20 step이다.
논문용 최종 규모·반복 수를 확정하는 설정이 아니며, 실제 실험용으로 복사해 조정한다.
조건 수와 반복 수에 코드상의 고정값은 없다.

예비 측정과 논문용 시작안은 각각 다음 명령으로 실행한다. 조건 선정 근거와 확정
절차는 [연구 기준 5절](research-goals.md#experiments)에 있다. 최종 측정 전에 예비
소요 시간과 변동을 확인하고 설정을 확정한다.

```powershell
python -B scripts/run_benchmarks.py benchmarks/pilot.json
python -B scripts/run_benchmarks.py benchmarks/thesis.json
```

## 진행률과 재개

전체 완료 비율·횟수, 현재 구현·개체 수·변경률·반복 번호와 현재/전체 경과 시간을
터미널에 표시한다. 현재 실행 중인 프로세스 안의 step 진행률은 표시하지 않는다.
다른 크기의 실행 시간을 단순 평균해 부정확한 ETA를 표시하지도 않는다.

**같은 명령을 다시 실행하면 자동으로 이어서 실행한다.** 같은 설정, 실행 파일·도구·
CMakeCache SHA-256과 Python 버전을 가진 가장 최근 폴더를 선택한다. 성공 CSV를
모두 재검증한 뒤 건너뛰며, 실패·중단·손상되거나 누락된 CSV의 실행만 재시도한다.
완료된 배치를 다시 호출하면 측정 없이 Excel/CSV 요약만 갱신한다.

```powershell
# 특정 결과 폴더를 명시해 재개
python -B scripts/run_benchmarks.py benchmarks/thesis.json --resume out/benchmark-suites/<결과폴더>

# 같은 조건을 처음부터 새로 측정
python -B scripts/run_benchmarks.py benchmarks/thesis.json --new
```

설정·바이너리·도구·빌드 설정·Python이 바뀌면 자동 실행은 별도 폴더를 만들고,
`--resume`으로 이전 폴더를 명시한 경우에는 오류를 낸다. 이전 버전 도구가 만든
결과 폴더는 재개 대상으로 사용하지 않는다. 재개 후에도 새 결과의 CPU·OS·빌드가
기존 성공 결과와 같아야 한다. 재개 시점이 다르면 시스템 부하·온도가 같다는 보장은
없으므로 시작·종료 시각을 함께 검토한다.

Ctrl+C는 현재 자식을 종료·회수하고 중단 상태를 저장한다. 프로세스 한 번이 재개의
단위이며, 중간 step에서 이어서 실행하지 않는다. 이전 CSV·로그·명령은 남기고 새
`attempt` 번호로 재시도한다. 강제 종료 때도 Windows Job Object가 연결된 자식을
종료한다. 완료 기록이 남기 전에 중단된 실행은 다시 측정한다.

## 설정 계약

JSON의 모든 필드는 `timeout_seconds`와 `order_seed`를 제외하면 필수다. 경로는 현재 작업 폴더가
아닌 **설정 파일 위치 기준**으로 해석한다. 알 수 없는 필드·중복 JSON 키도 거부한다.

| 필드 | 의미와 유효 범위 |
| --- | --- |
| `version` | 설정 형식 버전, 정수 `1` |
| `executable` | `<build>/App/Release/App.exe`; 인접 `CMakeCache.txt`의 VS2022 x64 기본 toolset 확인 |
| `output_directory` | 새 결과 폴더 생성 및 자동 재개 검색 경로 |
| `repetitions` | 양의 정수; 전체 조건 목록을 반복할 횟수 |
| `seed` | 세 구현에 공통으로 적용할 uint32 정수 |
| `dt` | 양의 유한 float32로 표현 가능한 고정 timestep(초) |
| `warmup_steps` | 0 이상의 정수 |
| `measurement_steps` | 양의 정수 |
| `conditions` | 아래 네 필드를 가진 비어 있지 않은 조건 목록 |
| `conditions[].implementation` | `oop`, `ecs`, `archetype` |
| `conditions[].boid_count` | 0 이상의 정수 |
| `conditions[].dummy_count` | 0 이상의 정수 |
| `conditions[].dummy_change_percent` | 0~100 정수 |
| `timeout_seconds` | 선택 사항, 실행당 제한 시간(양의 정수 초); 생략 시 제한 없음 |
| `order_seed` | 선택 사항, uint32; 반복마다 조건 순서를 재현 가능하게 섞음 |

모든 조건을 실행 전에 검사한다. bool·소수인 개수, ECS ID 범위를 넘는 총 개체 수,
step 수나 공통 입력 저장량의 산술 범위 초과도 거부한다. 실제 메모리 부족과 수치
overflow 등 실행 중 실패는 개별 실패로 남긴다. 실행 순서는 **반복 번호 → 조건
순서**다. `order_seed`를 생략하면 설정 순서를 사용하며, 지정하면 반복별로 섞는다.
원래 조건 번호와 실제 실행 순서를 모두 기록한다. 동일한 시뮬레이션 seed와 dt를
모든 조건·반복에 사용하며, 실행 순서용 seed는 시뮬레이션 입력에 영향을 주지 않는다.

## 결과와 실패 처리

새 배치는 UTC 시각과 UUID로 폴더를 만든다. 재개는 해당 폴더를 사용한다.
파일 이름에는 전체 실행 순서·조건 번호·반복 번호·시도 번호(모두 1부터 시작)를 포함한다.

| 파일 | 보존 내용 |
| --- | --- |
| `config.json` | 원본 설정 파일의 바이트 그대로 |
| `manifest.json` | 절대 경로로 해석한 설정, 실행 파일·도구·빌드 설정 SHA-256, Python 버전, 실행 순서 정책 |
| `CMakeCache.txt` | 실행 파일의 빌드 설정 사본 |
| `*.command.json` | 실제 argv 배열, Windows 명령 문자열과 자식 작업 폴더 |
| `*.csv` | App의 CSV v2 원자료; 실행 실패 시 없을 수 있음 |
| `*.log` | 해당 자식의 stdout·stderr와 실행 도구의 실패 사유 |
| `attempts.jsonl` | 각 완료·실패·중단 시도; 실행마다 flush·fsync하는 복구 원본 |
| `results.csv` | 실행별 최신 판정, 조건·시간·메모리 요약과 각 지표의 상태·사유; UTF-8 BOM |
| `results.xlsx` | Runs(최신 상태·대기 포함), Attempts(전체 시도), Metadata(실행 설정·식별 정보) |
| `summary.json` | 성공·실패·전체 실행 수 |

도구는 자식 프로세스가 종료된 후에만 다음 실행을 시작한다. timeout 시 자식을
종료하고 회수한 다음 계속한다. 이름 있는 Windows mutex로 이 도구의 중복 실행을
거부한다. 수동 App 실행이나 외부 프로파일링은 함께 실행하지 않는다.
실행 파일 SHA-256을 매 실행 전후 확인해 도중 빌드가 바뀐 실행을 실패 처리한다.

종료 코드 0이어도 CSV가 없거나 잘못되면 실패다. 형식 버전, 실제 조건·float32 dt,
Release·MSVC·단일 스레드 환경, step별 전체 시간과 네 구간의 시간·호출 수,
초기화·요약·프로세스 최대 메모리·저장량 항목을 확인한다. 중복·누락·범위 밖 step,
비유한·음수 측정값, 저장량 size/capacity 대응과 알려진 합계 오류를 거부한다.
전체 시간 합계·평균·updates/s, 구간별 평균과 이웃 Pair당 비용도 step별 원자료로
재계산해 대조한다(상대 허용 오차 `1e-9`, 절대 허용 오차 `1e-12`, 각 지표 단위 기준).
평균 전체 시간이 0일 때만 updates/s를, Boid 수가 0 또는 1일 때만 이웃 Pair당 비용을
`not_measured`로 허용한다. 전체 시간은 네 구간 시간의 합계와 별도로 검증한다.
실행 간 CPU·OS·컴파일러·빌드 플래그도 비교한다.

메모리 API의 미지원·실패는 빈 값과 상태·사유가 있으면 보존할 수 있다.
Sparse Set의 알려진 저장량 부분합(`partial`)도 허용한다. 이들은 실제 숫자 0과
구분되며, 결과가 성공이어도 모든 메모리 지표가 수집되었다는 뜻은 아니다.
`results.csv`의 종료 코드는 CSV 검증 실패라면 `0`일 수 있으며, timeout이나 시작
실패처럼 정상 종료 코드를 얻지 못한 경우 빈 값이다. 판정에는 `status`와 `error`를 사용한다.

시간·메모리는 Excel에서도 숫자 셀이며 미측정 값은 빈 셀과 상태·사유로 남긴다.
요약 열의 시간 단위는 ms(처리율은 updates/s), 메모리는 bytes다. 원본 step·상세
저장량은 각 실행 CSV에 보존한다. 표의 첫 행은 고정하고 필터를 제공한다.
Excel/CSV 요약은 완료 기록을 저장한 뒤 임시 파일에서 교체하며, 복구 원본으로부터
다시 만들 수 있다. Excel에서 `results.xlsx`를 열어 두면 Windows가 덮어쓰기를 막을
수 있다. 이때 경고를 표시하고 CSV·복구 기록을 계속 저장한다. Excel을 닫으면 다음
실행 완료 때 갱신되며, 이미 종료됐으면 같은 명령을 재실행해 갱신한다.

각 실행 후 결과를 저장하고 실패 후에도 나머지를 계속한다. 마지막에 성공·실패
수를 출력하고 하나라도 실패하면 도구의 종료 코드는 `1`, 모두 성공하면 `0`이다.
실행 전 설정·환경 오류도 `1`, Ctrl+C는 `130`이다. 도구 자체 중단이나 디스크 오류는 전체 실행을
중단할 수 있으며, 이 경우 완료된 `summary.json`이 없으므로 미완료 실행으로 취급한다.
